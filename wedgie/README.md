# wedgie

Jiro on a [wedgie](https://wedgie.dev): jiro-core as a MicroPython native module, `jiro_core.mpy`, and the apps that run it (README §2, §3). The wedgie keeps its own firmware (0.3.76, MicroPython 1.29.0), so the module is built for that MicroPython and checked on its qemu port before it reaches a device.

| Path | What |
|---|---|
| `natmod/rust/` | `jiro-natmod`: jiro-core behind an `extern "C"` interface, a `staticlib` for `thumbv6m-none-eabi`, position-independent, with no `.data` and no `.bss`. Its own Cargo workspace. |
| `natmod/glue/` | The C glue (`jiro.c`), the stack switch (`call_on_stack.S`), the interface (`jiro_api.h`) and the Makefile that links `jiro_core.mpy` |
| `scripts/` | The builds, the qemu vector run, the app's qemu play test, and the checks of `mpy_ld`'s rules, of the module's header and of the app limits |
| `check/` | The check app: it replays every golden vector through the module on a wedgie and shows PASS or FAIL per vector |
| `app/` | The Training app: the 16 levels, offline, at 15 Hz, with local best scores (README §8.1) |

## Building

```bash
bash scripts/bootstrap.sh wedgie          # arm-none-eabi-gcc, qemu-system-arm, MicroPython v1.29.0, pyelftools 0.32
bash wedgie/scripts/build-qemu.sh         # mpy-cross and the qemu firmware; prints the firmware's path
make -C wedgie/natmod/glue                # jiro_core.mpy, then the mpy_ld rules and header checks
python3 -I wedgie/scripts/qemu_natmod_vectors.py <firmware.elf> wedgie/natmod/glue/jiro_core.mpy . --all
bash wedgie/scripts/build-check.sh        # the check app in wedgie/check/, and its app limits
bash wedgie/scripts/build-app.sh          # the Training app in wedgie/app/, and its app limits
cargo build -p jiro-tools --locked        # native replay, which the play test checks against
python3 -I wedgie/scripts/qemu_app_check.py <firmware.elf> wedgie/app 137760
```

The bootstrap puts MicroPython and pyelftools in `~/.cache/jiro-wedgie` (`JIRO_WEDGIE_HOME` moves it); docs/TOOLING.md records the versions. Run the qemu check under a timeout, as CI does: a module that hard-faults hangs qemu instead of failing. For a vector that fails, it also prints the first tick whose state hash differs from the committed trace (README §6.6), within the first 1,024 ticks: a whole trace does not fit beside the stack in the qemu port's heap.

- **Link order.** For armv6m, MicroPython v1.29.0's `mpy_ld` builds the module's entry trampoline from `mpy_init`'s offset in its own section, before it lays out the sections. That is right only when the object defining `mpy_init` is linked first. The spike's first build linked the Rust object first: its trampoline jumped into the middle of `jiro_recorder_step`, and the module froze a wedgie on its splash screen and hard-faulted on qemu. The Makefile links the glue's objects first.
- **Size.** The module is 18,180 bytes, of which 17,944 bytes of code, and takes 18,760 bytes of heap once imported (M3.8's, without the renderer's exports, was 15,890 and 16,460). `natmod/rust` builds at `opt-level = "s"`, its smallest: at M3.8, 14,356 bytes of Rust code, against 15,474 at `"z"` and 18,296 at `2`; 15,606 bytes now.
- **Reproducible.** Two clean builds, in two directories, gave the same sha256; CI prints the size and sha256 of its own build between `=== BEGIN jiro_core.mpy ===` and `=== END jiro_core.mpy ===`.
- **CI** (`wedgie` job of `.github/workflows/ci.yml`) runs these steps and uploads `wedgie/check/` and `wedgie/app/`, each with the module, as the `wedgie-check` and `wedgie-app` artifacts, kept 90 days.
- **qemu's clock.** The qemu port's ticks assume a 25 MHz SysTick, which qemu's nRF51 clocks at 16 MHz, so one microsecond the port measures is 1,562.5 instructions under `-icount shift=0` (the vector run) and 195.3 under `shift=3` (the play test): measured with an inline-assembler loop of known length. A wedgie runs 125 instructions per microsecond at one instruction per cycle. The port's heap is 236 KB, which holds the play test's files, the screen buffer and a wedgie's free RAM.

## The module's interface

`jiro_core` exports `rules_version()`, `recorder_size()`, `shadow_size()`, `start(recorder, level, mode, run_nonce, level_index, stack)`, `step(recorder, mask, stack)`, `journal(recorder[, start, end])`, `journal_equals(recorder, buffer)`, `state_hash(recorder, stack)` and `replay(level, journal, weight_bp, stack[, trace])`, and for the renderer `status(recorder, out)`, `score(recorder, weight_bp)`, `paint(recorder, shadow, frame, colors, rect)` and `restore(recorder, frame, colors, x, y, width, height)`; `natmod/glue/jiro.c` documents the return values. The caller owns all memory: a `bytearray` of at least 64 KB for the stack, one of `recorder_size()` bytes for the Recorder and, to paint, one of `shadow_size()` bytes for the shadow of jiro-shell's dirty-cell diff.

- **The recorder buffer** holds a marker word, then the Recorder. `start` clears the marker, and writes it after the Recorder only when it succeeds; every other call that takes the buffer raises `ValueError` without it. So a buffer that no successful `start` wrote is never read as a Recorder. The marker does not guard against Python code writing into a started buffer: the app never touches it.
- **The renderer's exports** read the Recorder only. `status` writes 23 u16 fields: the end reason, ticks, time limit, lives, shield, invulnerability, cutting, claim and target, and the player's, the boss's and the three minions' cells (`natmod/rust/src/lib.rs`, `jiro_status`). `score` is the ended level's score, with the core's `level_score`. `paint` runs jiro-shell's dirty-cell diff (`Shadow`, which the browser's `DirtyCells` uses too) and paints the changed cells into the wedgie's 4-bit framebuffer, returning their bounding rectangle; `restore` repaints a rectangle of cells from the grid, under an entity that moved. They run on the C stack, in frames of at most 204 bytes.

## Stack and RAM

- **Stack.** The rp2 port gives C code an 8 KB stack, and the core builds its large structs on the stack, so `start`, `step`, `state_hash` and `replay` run on the 64 KB stack the app allocates (`call_on_stack.S`). The qemu port's 8 KB stack size is a soft limit the VM checks, not a physical stack: the qemu run checks that the core stays on the 64 KB buffer and fits it, and the wedgie run is the real check of the rp2 port. The qemu run measures the peaks over all 75 vectors: `start` 62,784 bytes, `step` 344, `replay` 44,040, of 65,536. Interrupts push onto the current stack: in some qemu runs `start` peaked at 62,816 bytes, one 32-byte exception frame more. On the RP2040 that leaves about 2.7 KB for interrupt frames. In-place constructors in the core would shrink the stack (plan M3.10).
- **RAM.** The wedgie reported 137,760 bytes free with no app, and 115,344 during a `wedgie.py debug` job (spike, [PR #42](https://github.com/detychey/jiro-ikusu/pull/42)). An app needs, in large blocks, the 64 KB stack, the 18,568-byte recorder buffer and the module's 18 KB: 102 KB. So an app allocates the stack and the Recorder first, while the heap is whole, then imports `jiro_core`; ships its code precompiled with `mpy-cross`, so that no parse tree is scattered over the heap; and reads one level or vector at a time.
- **The check app** holds at most one vector at a time: up to 8,172 bytes of journal read from its file, which `journal_equals` compares with the Recorder's in place. On qemu, with the heap filled to leave a given amount free, it passed with 137,760 bytes free in one block or with four 4 KB holes, down to 121,000 in one block and 120,000 with eight 1 KB holes, and failed with a MemoryError (an exception, not a freeze) at 120,000 in one block and 117,000 with the holes. The spike's smaller app, which held at most 5 KB per vector, passed down to 113,792 bytes free.
- **The Training app** allocates the stack, the recorder buffer and the 3,600-byte shadow, then imports `jiro_core` and `jiro_app.mpy` (5.4 KB), and reads its level file's index; it reads one level's 472 bytes at a time. In the play test at 137,760 bytes free, 19,728 bytes stay free after start, with a largest free block of 747 bytes: the play loop binds the screen's methods once rather than every tick, and the summary's few kilobytes come from garbage the collector frees. It passed down to 127,500 bytes free, and failed at 127,000 with a MemoryError on the module's 17,944 bytes of code (an exception, not a freeze). The ballast's free bytes are not always one block: they include holes it cannot fill, so the margin moves by a few kilobytes with the size of the files the test uploads before it. This is the RAM check of plan M3.9; M3.10, a smaller stack, is not needed.
- **Time.** On qemu's instruction count, replaying the 75 vectors takes about 19 billion instructions, the worst vector 572 million (M3.8 read qemu's microseconds as 1,000 instructions and gave 12.1 billion and 386 million; see qemu's clock above). At 125 MHz that is about 150 s, and the Recorder pass about as much again, so the check app runs for about 5 minutes. During a long replay the VM runs no scheduled tasks, so USB output stalls; the screen shows which vector runs.

## The check app

`check/` is a wedgie app (`mod` `jiro`, entry `run`). `jiro.py` allocates the core's stack and Recorder, imports `jiro_core`, then `jiro_check.mpy`, compiled from `check/jiro_check.py`. It reads `jiro_vectors.bin`, which `scripts/make_check_vectors.py` writes from every vector of `vectors/game/` and `vectors/levels/`, one record at a time. For each vector it checks replay's code, the Outcome, the tick count, traceKeccak and the last state hash; for a vector replay accepts, it plays the journal's inputs through the Recorder and checks its end reason, journal and final state hash. Before each vector it shows "vector i of 75" on the screen. It prints each result over USB, then shows PASS or FAIL per vector, eight to a page, as `ok 12 ture-split-boss-left`: the vector's number and the end of its name; green turns the page. The qemu run uses the same `read_case` and `check` on records of the same encoder.

`wedgie/scripts/check_app_limits.py` checks the wedgie's app limits on the files `wedgie.json` lists: at most 30 files and 256 KB, every name starting with the `mod`. The check app has 4 files and 230,797 bytes, the Training app 4 files and 33,048.

## The Training app

`app/` is a wedgie app (`mod` `jiro`, entry `run`, named Jiro Training). `jiro.py` allocates the core's stack, the recorder buffer and the shadow, imports `jiro_core`, then `jiro_app.mpy`, compiled from `app/jiro_app.py`. `jiro_levels.bin`, which `scripts/make_app_levels.py` writes at build time, holds the 16 levels of `levels/` with the weights of `seasons/calibration-1.json`, in slot order. The app checks that the core runs the calibration's rules version, and, when it starts a level, that the level id in the journal the core began equals the calibration's.

- **Level select,** outside play and never journaled: the joystick picks one of the 16 levels, green plays it. It shows the level's best score, and the free heap and largest free block after start.
- **Level start:** a fresh run nonce from `wedgie.rand(32)`, the wedgie's random source (README §6.3 allows any in Training; Training plays at `levelIndex` 0, as in the browser), then the field with a brief overlay of the level's name, target and lives, for 1.5 s before tick 0.
- **The tick,** every 66,666⅔ µs on an absolute schedule: tick k is due at t0 + ⌊k × 10⁶ / 15⌋ µs, kept as a running due time that advances by 66,666 or 66,667 µs, so `ticks_add`'s delta stays small however long a level is. A late tick runs as soon as it can, and the next stays on its own due time: no tick is skipped or stepped twice. A due time is never more than one tick ahead, so one that `ticks_diff` reads further ahead is more than 2²⁹ µs late, past its range, and runs at once: the app never sleeps for minutes on a misread due time. Each tick samples the controls once into the README §6.1 mask, held or pressed since the last sample, with D8's mapping (joystick, A green, B and X grey); Y (red) and the joystick press are never in it. Then the core's Recorder steps with it, and the app repaints: `restore` under the entities' old cells, `paint` for the cells that changed, the boss, the minions and the player on top, and `show_rect` for each entity's old and new cells and for the changed cells' rectangle. The player is drawn 6 pixels wide, a pixel larger than its cell on each side, in a black ring a pixel wider, so it stands out on the 4-pixel trail it cuts, on the claimed area and on the borders (round E1: a 4-pixel white dot was hard to see on the trail); its old cell and the cells around it are restored.
- **Between levels:** the summary screen comes first, then the USB output, which can block for 500 ms a print when a host holds the port open without reading it; presses made in the level's last moments and the first 0.5 s are discarded, so they do not skip it. It shows the end reason, the claim, the score (the core's, with the calibration's weight), the lives and ticks, the best, and the level's timing: the worst step, the worst draw, the worst tick and the overruns (ticks that ended after the next tick was due). Green goes back to the level select, on the next level after a clear.
- **Over USB** it prints the free heap and the largest free block after start, and after each level its end, claim, ticks, lives, score, timing and journal, in hex, which `jiro-tools replay` replays.
- **Best scores** are kept per level in the save `bests` (`/saves/jiro/`, which survives reinstalls), keyed by the rules version, the level id and the weight, as the browser's Training page keys them.

**The play test,** `scripts/qemu_app_check.py`, runs `jiro.py`'s `run()` unmodified on the qemu port, with `lcd`, `ui`, `save`, `wedgie` and `time` stubbed and the app's files in a RAM filesystem, after a ballast fills the heap down to the given free bytes. The `time` stub's `ticks_us` wraps 2³⁰ early in play, and on tick 70 jumps 600 s ahead, past `ticks_diff`'s 2²⁹ µs range, as a wedgie whose ticks fell that far behind would see it: the build before round E1's fixes slept for minutes there, and the test's timeout failed it. Scripted keys pick level 1, play 88 ticks with two captures, a fast cut, a shield tap, and Y and the joystick press held, then commit. It checks the journal (header, and events equal to the scripted keys' mask changes), the end, claim, ticks and score against `jiro-tools replay` of that journal, the stored best, the summary screen, and no overrun before the clock's jump, then one on every tick. At 137,760 bytes free, the worst tick (a capture) took 1.68 million instructions, the worst step 1.31 million and the worst draw 0.41 million; at 125 MHz and one instruction per cycle that is 13.4, 10.5 and 3.2 ms. The most rows pushed in a tick were 106, about 4.8 ms on a wedgie at 45 µs a row. The other 15 levels, played with the same inputs before the player's ring, stayed within 1.45 million instructions a tick and 136 rows. A wedgie's own numbers come from round E1 (`reports/wedgie-2026-11-02.md`).

## Installing on a wedgie

Download and unzip the `wedgie-check` or `wedgie-app` artifact of a CI run (or build it, above), and from its folder, with wedgie's CLI ([wedgie.dev/wedgie.py](https://wedgie.dev/wedgie.py)):

```bash
python3 wedgie.py install .
```

Press green on the wedgie to accept. The check app then shows its progress and results; the Training app its level select. Don't run `python3 wedgie.py debug` while the check runs: it stops the app and restarts it. Run it afterwards, to read `error.log` if the app ended on an error.

**If the wedgie hangs on an app,** for example on its splash screen with USB unresponsive: unplug it, hold both grey buttons (B and X) while plugging it in, which starts it without its app, then run `python3 wedgie.py uninstall`.
