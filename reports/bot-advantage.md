# Bot advantage

Generated by `jiro-tools playtest --merge` from the 8 shards of `reports/bot-advantage/`: rules version 2, seed 7, 200 six-level Challenge runs. Run k has the run nonce `nonce(7, k)`, plays the levels its draw names under Challenge headers (README §6.3, §8.2), and scores them at the calibration's weights. Every policy played the same 1200 games, so each comparison pairs the runs. Intervals: 95 % percentile bootstrap over the runs, 10000 resamples, the same for every statistic. Means in points, to a tenth; ratios to a thousandth; both rounded down.

The studied policy, `search`, searches each level's future with the core (plan M4.13). It spends at most 892857 work units per tick played, and a unit costs at most 56 ns on one container core, so it computes at most 749 ms per game second on one core. A search spends only the units accrued since the state it searches from became known, on the level it plays: the bot uses no `commitSlack`, no nonce preview and no second core. It pads half the ticks a level can spare beyond 300 (README §7.2: padding costs only the fewer-ticks tiebreak).

## Score ceiling

No play claims more than (claimable − B²) × 10,000 / claimable bp on a level, rounded down: the boss's B × B body covers only open cells (R4.6-1), which no capture claims. The ceiling run scores each drawn level at that claim, cleared: 135487.7 points on average. search reaches 0.985 [0.984, 0.985] of it, a share in thousandths, and the ceiling is 1.015 [1.014, 1.015] times its score.

## Reproduce

Shard i: `cargo run -p jiro-tools --release --locked -- playtest --policy search --runs 200 --seed 7 --shard <i>/8 --out reports/bot-advantage/shard-<i>.json` writes the same bytes. One level of a run: `cargo run -p jiro-tools --release --locked -- playtest --policy search --nonce <runNonce> --level-index <i> --out level.jrn` writes the journal the shard holds. Then `cargo run -p jiro-tools --release --locked -- playtest --merge reports/bot-advantage/ --out <this file>`.
